# Eval decisions

One line each. Newest at the bottom.

- The grader is trusted only after it agrees with the user on 30 hand-labelled pairs, answering the same yes/no questions; below about 90% agreement the grader prompt is fixed, not the labels.
- Two gates: a build may replace the daily one, and the result must convince a stranger; so confidence intervals, never single runs.
- Two comparisons in one table: control says whether the proxy is safe, previous build says whether a fix helped.
- Corpus is a fixed stored set of sessions, not daily use.
- Planning arm runs Opus 5 at xhigh; implementation arm runs Opus 5 at high; runs 3–6 in findings.md are not comparable.
- Session content stays outside the repo; scripts, case manifest, and result tables are committed.
- Manual, one command, no CI.
- Replay is fresh: a build evicts a stored prefix from an empty state, because the eval compares builds, not history.
- Names live in CONTEXT.md; the model that scores a pair is the "grader", never a "judge".
- This file is one sentence per decision; ADRs are not used.
- Planning cases are text turns only; tool behaviour is not graded there, though a proxied tool call where control answered in text is counted as cost.
- Implementation tails always fork from one recorded control run at the last turn under 110k, never from scratch, because the proxy is inert before its first trip so the prefix is identical either way.
- Verified 2026-09-04 on Claude Code 2.1.261: `claude -p --resume <id> --fork-session` continues a recorded session under a new id and leaves the parent transcript unmodified.
- The implementation prefix is recorded fresh by run.sh on Opus 5; the planning corpus reuses an old transcript (see below).
- Planning replay reuses the recorded human turns and regenerates one model turn per case; nothing simulates the user.
- The corpus is two sessions, the most complex implementation session and the biggest planning session.
- Proxied arms never compact; a control's compaction is whatever Claude Code does on its own at that window.
- Implementation arms never compact: control runs at the 1M window straight through, because no engineer lets auto-compaction interrupt an implementation.
- The planning session is recorded at the 200k window with the 1M flag off, so Claude Code auto-compacts between turns on its own; no manual /compact.
- Planning recordings go through the proxy with eviction disabled and dumps on, so every exact request body is captured.
- The grader runs on Sonnet first; a question moves to Opus only when Sonnet disagrees with the hand labels on it; Fable is never used.
- The implementation task is mastra #18877 from the stored plan, scored by the PR's two test files, which the user wrote and which are unmerged as of 2026-09-04.
- Cost is reported as four token classes per arm, fresh input, cache write, cache read, output, plus notional dollars at API list price, because the proxy's rebuilds move tokens between classes.
- The planning corpus is the user's existing biggest planning session, not a new recording; its typed turns and manual compaction points are reused, and only the model turns are regenerated on Opus 5 xhigh.
- Planning request bodies are rebuilt from the transcript with the current Claude Code system prompt and tools, which is approximate and stated as such.
- Implementation has two arms, proxied and control at 1M; three tails per arm while fixing, five per arm for a published number.
- A tail restores both halves of state: the forked conversation and a fresh worktree at a snapshot commit taken at the fork point.
- No pass threshold before the first run; the bar is written down after the first result and before the second run, then never moved.
- Control is a stored baseline, not a per-run arm: control planning samples and control tails are recorded once and reused, keyed by model, effort and the captured request template, and rerun only when one of those changes. Each iteration pays for the proxied arm only.
- A replay mode runs the stored planning prefixes through the proxy against a fake upstream with no model calls and diffs the eviction outcome, stubs, sizes and rebuild count against the previous build. It is the check run after every fix; it is not scored and is exempt from the bar rule.
- Quick and full modes are for the intelligence question and run once per behavioural change, not per bug fix.
- No case manifest. Eligible planning cases are listed by rule at run time; quick mode takes every fourth one; each result document carries the case list it ran; the previous-build comparison refuses when case lists differ. Supersedes the manifest in the earlier committed-artifacts bullet.
- The planning grader does not check claims against the repo, so no repo commit is paired with a case. The commit could only be guessed from timestamps, which made that question's verdicts unreliable. The implementation grader keeps its read-only tools over the tail's exact worktree.
- Planning cases are replayed as real Claude Code turns, forked from the stored session through the Agent SDK with the recorded user turn as the prompt, not as raw API calls from a rebuilt request body. Claude Code builds the request and runs tools, so nothing about the harness is reconstructed or has to be proven equivalent. Supersedes the rebuilt-bodies bullet; no request template is captured.
- Planning cases come only from before the session's first compaction, 21 typed turns between 110k and 160k in the chp99 transcript, so both arms fork the same untouched copy and no derived transcript is needed. Later stretches are out of scope; the tails cover deeper contexts. Supersedes the derived-transcript bullet.
- Because a planning fork can read files, each case runs in a worktree of the chp99 repo at the last commit before the case timestamp. This reverses the earlier drop of the per-case commit; it is approximate and stated. The planning grader still asks no repo question.
- Planning forks and tails run on Claude Code's own login. The API key is used only for count-tokens and the graders.
- The planning grader asks one question only, is the proxied answer at least as good a next turn as the control answer, with the full history in its prompt and read-only tools over the case worktree. No fault or diagnostic questions.
- Both graders read the repo the answer was written against with three read-only tools; for planning that is the case worktree at the nearest earlier commit, the same approximation the forks already accept. Supersedes the no-repo-question bullet.
- Pairs are shown to the grader in random order, one call per pair, not both orderings. The noise floor detects position bias; both orderings are added only if the first run shows it.
- Graders run at effort high.
- A grader call is capped at 40 model turns. Capped and unparsable calls, and forks that hit their turn cap or ended without text, are Unknown with the reason recorded; each is printed as a warning when it happens and listed by case in a problems section of the result document and the report, never only counted.
- The implementation grader asks the same single comparative question as planning, over a proxied tail's diff and a control tail's diff with both worktrees readable: is diff A at least as good a change as diff B, where as good as means does what the plan asks, breaks nothing, is as simple as the job allows, and reuses existing code. The four fault questions are dropped; ground-truth assertions remain the deciding number and the grader is a second column with its own noise floor.
- The implementation grader runs on Opus 5 at effort xhigh from the start, not Sonnet-first: one heavy code-review question over a few dozen pairs, so the stronger model is cheap. The planning grader stays Sonnet-first. Supersedes the Sonnet-first bullet for implementation only.
- Graders call the API directly through the Anthropic SDK, never through `claude -p`, so every model call the eval makes itself can be faked at one HTTP seam in tests.
- The eval builds and starts its own proxy child per planning case and per proxied tail, on an ephemeral port; the manually started proxy is never used.
- Worktree snapshots during the recording are hidden git commits made through a temporary index and commit-tree under a private ref namespace, one per tool-use id, so the agent's git commands see nothing. The SDK's file checkpointing is not used because it misses shell-command changes and rewinds in place.
- Planning cases and tails both fork through the Agent SDK's resume-at option. Two smoke checks precede any build: a copied transcript under another worktree's project directory resumes by id, and a resume-at fork at a model turn given the recorded user turn as prompt produces one turn.
- The bar file is enforced by the command: it refuses a second scored run while the file is missing.
- Verified 2026-09-05 on Claude Code 2.1.261 with Agent SDK 0.3.261, by `eval/smoke`: a transcript copied under a new session id into another worktree's project directory resumes by that id and answers from the recorded history, even though its entries still carry the original session id.
- Verified the same day: a `resumeSessionAt` fork at the kept turn's last chain entry, with `resumeDropsTurn` naming the dropped turn's prompt, is not refused, produces exactly one turn, and leaves both the copy it resumed and the recording it came from byte-identical.
- Claude Code files a session under the *resolved* working directory, every non-alphanumeric replaced by a dash, so the eval resolves a case worktree's path before placing a transcript copy; a symlinked corpus directory would otherwise put copies where nothing looks for them.
- Hidden snapshots are invisible to `git status`, `git log`, `git ls-files` and `git branch`, but `git log --all` lists them because `--all` means every ref under `refs/`; that leak is accepted and recorded rather than defended against.
- A fork keeps the parent's uuids for every entry it kept and mints fresh ones past the fork point, so a fork's kept prefix can be matched to its parent's by uuid with no transcript parsing.
- Snapshots hang off the recording's HEAD, not off each other: a chain would put the whole run's snapshot history into every tail's `git log` once the snapshot is checked out.
- Planning stays one isolated fork per case, one turn each, rather than one continuous run replaying every turn in sequence. A continuous run is closer to real use and would measure whether damage compounds, but it cannot be parallelised, costs about an hour per run, and needs several runs per arm for statistics. Depth comes from choosing deeper cases instead, which is free. Revisit if the isolated forks show nothing.

- Measured the same day: each compaction writes a new root, a `system` entry with a null parent carrying the compaction summary, while the conversation spine's parent links run through the compaction unbroken. Locating compactions must not rely on finding a compaction summary in the chain. - The grader's request carries one prompt-cache breakpoint, on the message holding the question and the two answers. Measured 2026-09-08: the system prompt and the three tool schemas come to 465 tokens together, under the roughly 1024 the API caches at all, so a breakpoint on the tools would be accepted and cache nothing — the failure is silent, since a prompt under the minimum is not an error. Everything above the breakpoint is fixed for the call's life, so every turn after the first reads it back. The tool results accumulating below it are not cached: moving a breakpoint down them each turn means `setMessagesParams`, which drops the runner's tool cache and would re-run tools already answered.
- Caching that never fires is reported once for the whole run, not once per call. Calls that sent more than 2,000 prompt tokens are expected to have read from the cache; if not one of them did, the run carries a problem entry naming how many tokens were written and never read back. The threshold sits clear of the API's minimum so that a short call, correctly not cached, does not raise it. Per-call warnings were rejected: if caching is broken it is broken for every call, and a line printed a hundred times is one nobody reads. One read anywhere is enough to call it working — a single call that missed is an expired entry, not a misconfiguration. The reason it is reported loudly at all is that misconfigured caching is worse than none: a cache write costs more than an ordinary prompt token, so a prefix that changes every call pays a premium to store something never read, and nothing else in a run's numbers moves when that happens.
- A call's prompt size is read as `input_tokens` plus both cache counts, never `input_tokens` alone, which is only the uncached part and so falls as caching starts working; a size threshold reading it by itself would quietly stop firing the moment the cache began doing its job. `GraderCall` records that size for the last turn, which is how full the context was when the verdict was decided. Verified against the real API 2026-09-08, two Sonnet grader calls over one pair: the static prefix measured 2,132 tokens and was written once per call and read back on every turn after the first — 8,528 read over 5 turns and 23,452 over 12, both exactly 2,132 times the turns after the first. Two things that verification settled and the fake could not. Cross-call caching never hits: every pair carries different answers, so no two grader calls share a prefix, and each call writes the block afresh. And the cached block is a small share of what a long call sends — the 12-turn call finished at 34,160 prompt tokens with 2,132 of them cached, the rest being the accumulating tool results, which is the larger half of the saving and is not taken.
- The grader's request carries two prompt-cache breakpoints, not one: the fixed one on the question and the answers, and a second that moves onto the newest tool result every turn. Supersedes the one-breakpoint bullet. Everything above a breakpoint is cached and everything below is not, so a mark that never moves caches the opening line and leaves the tool results — most of a long call's prompt — re-sent whole on every turn. The old mark is cleared before the new one is set, because the API allows four and a call may take forty turns.
- The grader runs its own tool loop against `messages.create` rather than the SDK's `toolRunner`. Supersedes the reading of the one-breakpoint bullet that said the tool results cannot be cached. `toolRunner` cannot do this: `setMessagesParams` is the only way to edit the request mid-loop, and it sets an internal `#mutated` flag that makes the runner skip appending the model's reply to `messages` and skip the stop-reason check, so the conversation stops advancing and the loop spins to the turn cap. Working around that means appending the reply by hand and depending on the exact internal order of the runner's steps, which is not a promise the SDK makes. The loop we replaced it with is four steps — send, record the reply, run the tools it asked for, record the results — and owning it is cheaper than owning a workaround for someone else's. The earlier claim that `setMessagesParams` re-runs answered tools was wrong: the results are already in `messages` and nothing re-runs.
- Verified against the real API 2026-09-08, two Sonnet grader calls forced to read widely. Eleven turns, finishing at 54,472 prompt tokens: 286,537 tokens read from cache and 53,184 written. The written total is within 3% of the final prompt, which is what incremental caching looks like — each turn writes only what it added. Against the fixed breakpoint measured the same day, 12 turns finishing at 34,160 with 23,452 read, that is twelve times the cache reads. Supersedes the closing claim of the prompt-size bullet that the larger half of the saving is not taken. The cost stands where it always did: a short call still writes a tail entry on its last turn that nothing reads back, and cross-call caching still never hits, because every pair carries different answers.

- Cases are cut at 80k of rebuilt prefix, not the proxy's 110k trip threshold, and the two are not in conflict. Cutting at 110k of rebuilt prefix would therefore drop turns that were past 110k in life, and drop them silently — the case list just comes back shorter. - A case's depth is read from the model turn that answered it and nothing is rebuilt or measured with count-tokens. - Replay's input is a recording, not a rebuild. A real Claude Code session is driven by the corpus session's own prompts with the proxy in front and `ONEPASS_DUMP_DIR` set, and the proxy writes every request body it is handed to disk untouched before it evicts anything; replay sends exactly those bytes back through a proxy child. This is what makes the three rules keyed on injected text — attached files, task notifications, and the protected read-input marker — testable at all: none of their text appeared in a single one of the 37 rebuilt bodies, so all three could have been deleted with replay still reporting every case identical. Supersedes the replay bullet's "stored planning prefixes".
- Replay feeds every recorded request through **one** proxy child, in the order the session sent them, and reports on the ~30 deepest. Eviction is monotonic — what the proxy does at one request depends on everything it took before — so a fresh child per request, or a run over the deep subset alone, gives the proxy a state history that never existed. Correctness comes from the full sequence; the readable table comes from the subset. Supersedes the one-child-per-case design.
- The recording session bills the Claude subscription and never `ANTHROPIC_API_KEY`. `eval/record.sh` unsets both `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` and then refuses to start if either survived, because the key lives in this repository's `.env` and the documented way to run the eval sources it — any shell that has, or any process inheriting from one, silently bills the key.
- The proxy logs its trip decision on every request entry (`overThreshold`), separately from the `trip` entry it writes only when something was actually evicted. Over the line with nothing eligible was previously indistinguishable from a small quiet request: case `turn-724` of `eval/results/3d1bb98-20260908T232351Z.json` reported 121,463 estimated tokens — past the proxy's own 110k — with `tripped: false`. It is the failure most worth catching, so replay counts it in its own right.
- Replay stopped tracking two values that could not move. The body handed to the proxy is a file on disk, identical for every build, and the fake upstream reports no cache creation so no rebuild is ever classified against it — "all six values agreed on all 37 cases" was really three. The recorded size stays on each outcome to say how deep the request was and is never counted as agreement.
- A run's label calls itself dirty on uncommitted changes anywhere in the repository, not only under `proxy/`. Three documents in `eval/results/` say build `3d1bb98`, `dirty: false`, and were produced by three different versions of the eval, one of which changed the case threshold.
- A dump's name is the clock and then the count the proxy wrote it in, not the clock alone. Name order has to be arrival order, because replay sorts the directory and feeds the sequence through one child; eviction is monotonic, so a pair read the wrong way round hands the proxy a state history the session never had and every request after them inherits it. A millisecond holds several requests of a busy session, and the collision suffix that first covered that — `<stamp>-001_v1_messages.json` — sorted *before* the name it collided with, since `-` sorts below `_`. A per-process counter in every name makes the ordering total instead of nearly total.

- The implementation grader is Claude Code itself, run non-interactively — `claude -p` on Opus at effort max, with Read, Grep and Glob and no other tool, started in a scratch directory holding only the plan, the two diffs and the question, with both finished repositories attached read-only — rather than a direct SDK call to the API; supersedes the direct-SDK bullet for the implementation grader only, and supersedes "Opus 5 at effort xhigh" for it. The planning grader is untouched, so the HTTP seam the tests fake still covers every model call the eval makes itself.
- Every implementation pair is graded in both orderings, always, and one outcome is derived from the two verdicts — Yes/Yes is *same*, Yes/No and No/Yes name the preferred side, No/No and any Unknown are *no clear answer*; supersedes "one call per pair, both orderings only if the noise floor shows position bias", because one call cannot tell a preference from a position bias and the second call is the cheap half of the pair.
- The implementation grader is trusted when two same-condition pairs both come out *same* and five of its reasons, picked by the user, are checked against the files they cite and hold; a preferred arm on a same-condition pair, or one false citation, sends the prompt back to be fixed and all calls to be rerun, never the labels. Supersedes "30 hand-labelled pairs at 90% agreement" for the implementation grader only; the planning grader's rule stands.
- A trip must newly evict at least `ONEPASS_BATCH_MIN_TOKENS`, default 20,000, or the whole batch is held back and its content waits for a later request where the batch clears the bar; `0` restores the old behaviour exactly. A trip's cost is a prompt-cache rewrite whatever it removes, so a hundred small trips cost a hundred rewrites and remove no more than a few large ones would.
- The proxy reports requests over `T + 40k` on an alarm line in the log and does nothing else about them. A hard ceiling was rejected: the size the alarm names comes from the un-evictable floor, which no amount of eviction can bring down, so a ceiling could only fail requests the proxy is unable to shrink.
- The default trip threshold moves from 110k to 80k, by the rule agreed before the measurement: with the batch minimum on, replay at T=80k gave 3.3 trips per 100 requests (≤ 10) and a peak of 89k sent (≤ 140k). Measured on `harbor-make-mips` at build `e2fc221`.
- The implementation grader is trusted by three checks that do not need anyone to read the repository, not by two same-condition pairs coming out *same*: a **positive control** — a pair whose answer is already known from the ground-truth tests, which the grader must get right; a **self-pair** — the same change on both sides under two tokens, which must come out *same*; and a citation check — a random sample of its reasons resolved to the lines they name by `eval/grade/cite.mjs`, none of which may be false. Measured 2026-09-09 on Step 1's repos: the two controls, same task and no proxy in either, came out *control3 preferred* in both orderings with reasons that hold when opened, so two runs of one condition are two different changes and *same* was the wrong requirement — it counted real between-run variance as grader noise, and no honest grader could have passed it. A same-condition pair still runs and still reads: its answer must follow the arm across the swap, not the slot. Supersedes "two same-condition pairs both come out *same*"; the five user-checked reasons stand as the ideal, with the sampled machine-resolved check as the fallback when the user cannot navigate the material, labelled as such wherever it is cited. The planning grader's rule stands.
